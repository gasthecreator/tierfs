# Threat model

tierfs holds the only copy of files while they are offloaded, so the threats that matter are mostly **loss and corruption**, then **disclosure**.
This is a living document; each row names the control and where it is tested.

## Assets
1. The user's files (content, names, sizes, attributes).
2. The master key and its recovery phrase.
3. The ledger (what exists where) and the quarantine (the last local copies).

## Trust boundaries
- **The Mac** (trusted while running; compromise of the Mac is out of scope).
- **Storage devices** (untrusted for confidentiality, integrity and honesty: they may rot, lie, lose data, be restored from old backups, or be stolen).
- **The network between them** (untrusted; the protocol has no encryption or login, so it is loopback-only by default).
- **The kernel / FUSE-T / macOS NFS client** (trusted to behave; known to have bugs: ADR-0006).

## Threats and controls
| # | Threat | Control | Evidence |
|---|---|---|---|
| T1 | A bug or crash destroys the only copy during offload | Move-to-quarantine, gated purge, intents journaled before the filesystem is touched, recovery at start | `tests/dropengine_test.cpp` (every crash point), ADR-0003, ADR-0004 |
| T2 | A device returns corrupted or wrong data | Chunks are AEAD-sealed with their id as associated data; ids are keyed HMACs of the plaintext; whole-file HMAC on recovery | `tests/crypto_test`, overlay and recovery tests (rot, swapped chunks, lying device) |
| T3 | A device silently lost or never had a copy | Challenge audits with one-time precomputed responses before any destructive step; replica weight needed (K=2.0) | `tests/replicator_test.cpp`, `tests/dropengine_test.cpp` |
| T4 | A device is restored from an old backup or re-initialised | Epoch and sequence tracking mark it suspect; its replicas stop counting until re-audited | `tests/replicator_test.cpp` |
| T5 | Two copies of the same data are confused (replay, swap) | AAD binds volume id, chunk id, file id and version | `tests/crypto_test.cpp` |
| T6 | A file is modified while being moved | Write gate (`FileGate`): a file with writers cannot be frozen; generation counters invalidate stale replication | `tests/overlay_write_test.cpp` (stress with drops) |
| T7 | The key is lost with the Mac | Recovery phrase (16 checksummed groups) proven by retyping three groups at setup; `tierctl check-phrase` | `tests/init_test.py` |
| T8 | An attacker with the phrase reads everything | Out of scope: the phrase is the root secret; keep it on paper, off the Mac | docs/RUNBOOK.md |
| T9 | A manifest or path from a device escapes the restore directory | Path sanitising (`..`, NUL, control chars, symlink components); setuid bits never applied; exclusive rename | `tests/recovery_test.cpp` (hostile manifests) |
| T10 | A malicious local process talks to the control socket | Socket is mode 0600 in the user's state directory; commands are the user's own | `tests/daemon_test.cpp` |
| T11 | The folder is unmounted and the scanner "forgets" every file | Refuses when more than half (and more than 10) tracked files are missing or the folder cannot be read | `tests/scanner_test.cpp` |
| T12 | Names that differ only in case or Unicode form collide | Folded unique key (ADR-0005) | `tests/ledger_test.cpp` |
| T13 | Traffic on the device network is read or altered, or someone impersonates the device or the Mac | Content is encrypted and authenticated end to end. Protocol v4 adds mutual authentication with a pairing secret, a fresh ephemeral key per connection and sealed, counted frames. A paired device refuses plaintext clients and any peer without the secret, drops peers that stall in the handshake, and may listen on the network; an unpaired device stays plaintext and loopback-only | `proto/PROTOCOL.md`, ADR-0009, `tests/securechannel_test.cpp`, `tests/deviceauth_test.cpp`, `tests/pairing_test.py`, `tests/recovery_test.cpp` (drill 15) |
| T14 | A kernel or NFS-client bug panics the machine | Never mount-test on the development Mac; CI never mounts | ADR-0006 |
| T15 | A file leaves the Mac although no backup holds it (new or edited since the last backup, or the backup is stale) | The backup statement is dated; the ledger refuses to drop or purge a file created or changed at or after it, or when it is older than 30 days; the policy does not plan such files | ADR-0007, `tests/ledger_test.cpp`, `tests/policy_test.cpp`, `tests/daemon_test.cpp` |
| T16 | A device (or a tool talking to it) deletes data it should keep, or garbage collection destroys the only copy | The ledger decides first and records it (hash-chained); live files never lose their current version, and an older version goes only when a newer one is held with full weight by fresh audits; deleted files wait out a retention period and quarantined bytes; the device deletes only named manifests and only unlisted chunks (a database trigger refuses to delete a listed chunk), only for a pairing that may delete or with `--allow-delete`; what is deleted waits in the device's trash for 7 days and can be restored (ADR-0017); an unknown or foreign device is never asked; GC is off unless asked | ADR-0010, `tests/gc_test.cpp`, `tests/ledger_test.cpp`, `tests/devicestore_test.cpp` |
| T17 | Someone on the network announces a fake device (or a copy of a real one) to be followed, or floods announcements | An announcement is only a locator: it is followed only if it names a key id the Mac holds a pairing secret for and says it is paired; the connection then needs the secret on both ends (a forged one fails to authenticate and attaches nothing); an unpaired device never advertises | ADR-0013, `tests/discovery_test.cpp`, `tests/daemon_test.cpp` |
| T18 | The disk fills and the person is never told (slow tick, notification not shown), or is told to do something that cannot work | Free space is checked on its own thread every 30 s; a notification that could not be shown is retried and reported; the text names the first blocker; nothing ever moves without the approval of ADR-0012 | ADR-0014, `tests/policy_test.cpp`, `tests/daemon_test.cpp` |
| T19 | A lost, stolen or wiped phone that held a copy; the pairing code leaks from the phone's screen | Chunks and manifests are encrypted by the Mac before they arrive, so the phone's storage reveals sizes and sharing only; at least two copies are required before a file leaves the Mac; the code is shown only on the phone (no screenshots or recent-apps preview, cleared when the app leaves the foreground) and can be replaced (`Make a new pairing code`, then every Mac pairs again); the store is app-private and excluded from backup; an unpaired store is never served | ADR-0015, `android/README.md` |
| T20 | Malformed or hostile input to a parser (frames, handshakes, requests, text) crashes or exhausts a device or the daemon | Bounds-checked reader; frames read incrementally; strict parsers with properties checked by a seeded fuzzer (accepted input is valid and re-encodes the same; no flipped bit of a sealed frame is accepted; a server survives mutated requests and keeps an intact store) | `tests/fuzz_test.cpp` |

## Known gaps (tracked, not hidden)
- A leaked pairing secret lets its holder impersonate the device or that Mac until it is revoked (`--revoke-pairing=KEYID`, ADR-0016; effective at once, other Macs unaffected); a device with only the original single `pairing.key` still shares one secret among all its Macs. On the device the secrets are 0600 files in the store directory, readable by anything running as that user; there is no rate limiting beyond the handshake deadline and the 64-connection cap. Devices that stay unpaired speak plaintext and must stay on loopback. A pairing added while the server runs works at once but is announced on the network only after a restart.
- The FUSE-T mount layer is unproven (it once panicked the kernel): nothing here is claimed about behaviour through a mount, including whether FUSE-T hands lock, link and `use_ino` requests to the driver (ADR-0006, ADR-0018).
- There is no iPhone agent: iOS suspends background apps, and the device server must stay up. There is no signed, notarized distribution of the Mac tools or the menu-bar app (that needs a paid Apple account); the Android APK is signed with a key of your own.
- The key lives in the login Keychain (this device only) when set up with `--store keychain`; the older key-file and `dir:` forms are development-only and leave the key readable by anything running as you. Any process running as you can ask the Keychain for the item once macOS allows it.
- The Android agent has only been run on an emulator. A phone that is lost still holds encrypted chunks and the pairing secret (private to the app, but readable on a rooted or compromised phone). Its pairing secret cannot be replaced remotely, so treat it as burned: remove the phone from the daemon's `devices=` and replace its copies; the data on it is encrypted with keys that never leave the Mac.
- Discovery announces the key id of a paired device to the local network; the id does not reveal the secret, but it tells observers that a device exists and lets them tell devices apart. Announcements can be forged to make a device look missing (the daemon then reports it as not found or not attached). mDNS does not cross networks: a device elsewhere needs an address.
- The low-space warning is a text notification polled every 30 seconds; it needs a logged-in user session, and macOS offers no hook for its own warning.
- Chunk ids and sizes leak the file-size distribution and which files share content (deduplication is visible to a device).
- Advisory locks are emulated inside the daemon: they are not visible to processes that bypass the mount (that is what advisory means), and there is no deadlock detection (a stuck waiter is ended by interrupting it). Hard-linked names share their locks (ADR-0018). Nothing about the safety of data depends on them.
- Garbage collection trusts the chunk list the Mac sends with a manifest: an authenticated Mac that lied could make a device sweep chunks a manifest needs, and an open device (loopback, `--allow-delete`) trusts any local process with that power. Since ADR-0017 that is undoable for the retention period (7 days by default): the files wait in the device's trash and `--restore-trash` puts them back; after that they are gone, and a device started with `--trash-days=0` has no such net. A device that missed a deletion keeps the old data (and a restore from it can show a deleted file) until the next run reaches it.
- The backup gate trusts the owner's dated statement: `tierctl check-backup` shows what macOS reports, but nothing proves a given file is inside the backup. Offloaded files drop out of later backups of the folder (older backups and the devices keep them).
